## Context

The portfolio articles represent Gladwin's technical work across AI developer tools, WebGL spatial mapping, IoT telemetry, Linux systems administration, and full-stack software development. To ensure case studies demonstrate the principles of professional portfolio development, the articles must adopt a standardized 10-section structure, write in an authentic first-person engineering voice, clearly delineate personal contributions, explain technical decision-making, and present evidence-based outcomes without fictitious metrics.

## Goals / Non-Goals

**Goals:**
- Rewrite all 12 Markdown files in `content/case-studies-md/` according to the standardized 10-section template:
  1. Title & Executive Summary
  2. Overview
  3. Problem and Context
  4. Objectives and Requirements
  5. Approach and Process
  6. Solution and Key Features
  7. My Role and Contributions
  8. Challenges and Decisions
  9. Results and Validation
  10. Lessons Learned and Future Improvements
  11. Closing and Project Links
- Use first-person active voice ("I designed", "I implemented", "I configured") to reflect authentic technical ownership.
- Maintain transparent technical credibility: state clearly when a project is an academic prototype, competition entry, or freelance client implementation.
- Preserve verified links to real repositories and live sites.

**Non-Goals:**
- Fabricating user adoption statistics, client revenue, or production deployment scale not grounded in actual records.
- Altering existing data schemas or routes.

## Decisions

### 1. Unified Narrative Voice
Adopt first-person active engineering voice. Clearly distinguish between individual responsibilities (e.g., backend API development, AWS EC2 Linux server provisioning, Three.js WebGL scene optimization) and general project context.

### 2. Evidence-Based Validation Reporting
Present real technical evidence:
- Functional verification: successfully tested workflows, JWT auth validation, sensor reading ranges.
- Performance benchmarks: measured WebGL frame rates (58–60 FPS), local CLI response times, and sensor interrupt sampling frequencies (500 Hz).
- Explicit status disclosure: explicitly identify projects as functional prototypes, competition builds, or production-grade demonstrations.

## Risks / Trade-offs

- **[Risk] Long articles causing fatigue** → **Mitigation**: Maintain scannability with informative subheadings, short paragraphs, and a sticky Table of Contents.
